# A Day in Site Reliability
A very common problem you face when running infrastructure for mission-critical software is making changes to the infrastructure or platform without crashing its clients — microservices, cron jobs and integrations you don't even know are there.

To minimize service downtime, SREs tend to perform these changes during low demand periods like off working hours or during weekends (if the product allows it). Although this is how you usually go about it in the industry, this has a downside very similar to "[no friday deploys](https://charity.wtf/p/friday-deploy-freezes-are-exactly-like-murdering-puppies)":
> "If you block devs from merging on Fridays, then you are sacrificing a fifth of your velocity and overall output. That's a lot of fucking output." —— Charity Majors

Let's exercise that a bit with an example scenario:

> Imagine that you own a set of VMs and use them to run a system composed of microservices inside containers. Consider that 10% of the containers run a mission-critical process.  
Let's say you need to do a maintenance task that requires downtime, such as doing an OS upgrade.  
Given that the microservices were designed to run 24x5, how do you maximize the availability of the system?

Unpredicted downtime is at the core of [systems engineering](https://en.wikipedia.org/wiki/Systems_engineering), which concerns both Software Engineers (SWE) and Site Reliability Engineers (SRE). When taking a chance at this problem, Software Engineers might broadly answer with "horizontal scaling". And that's the answer you'd expect a SWE to immediately think of during a system design session: it restricts itself to the application domain (["userland"](https://unix.stackexchange.com/questions/137820/whats-the-difference-of-the-userland-vs-the-kernel)) by addressing temporary downtime with redundancy.

SREs on the other hand are the ones responsible for ensuring there are enough machines to run the containers. They're naturally inclined to attempt an operational solution like splitting the set of VMs into two sets: one running the old OS version and another running the new OS version. Applications are iteratively migrated from the first group to the second group, and in case of error the migration can be halted or retried, resulting in minimal downtime. 

This [greedy](https://en.wikipedia.org/wiki/Greedy_algorithm) solution is widely known as "blue-green deployment", which can be rephrased as: "Provision two sets of VMs, one running OS version 'OLD' and another running OS version 'NEW'. Assign each container to VMs from the first set; then once they're stable move them to VMs from the second set.If they fail to run, move them back to X."

Also notice that both algorithms make use of partitioning as a principle of multi-tenancy.
